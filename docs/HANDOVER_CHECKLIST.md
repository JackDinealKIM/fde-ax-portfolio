# B. 운영 인수인계서

## B-1. 시스템 개요

| 항목 | 내용 |
|---|---|
| 서비스명 | 한빛리빙 사내 AI 지식베이스 (`hb-kb`) |
| 목적 | ERP·규정·CS 로그 통합 검색, 반복 업무 3종 자동화 |
| 사용자 | 임직원 18명 (관리자 2명) |
| 구성 | `kb-api`(FastAPI) · `kb-worker`(인덱싱) · `pgvector` · `ollama`(내부망) · `kb-ui`(정적) |
| 모델 | llama3.1:8b-instruct-q4_K_M (폐쇄망) / 외부 API 미사용 |
| 네임스페이스 | `kb` (k3s 클러스터 `hb-prod`) |
| 접속 | https://kb.hanbit.local (내부망 전용) |

```
사용자 → Ingress → kb-ui(정적) → kb-api ─┬─ pgvector (검색)
                                        ├─ ollama (생성)
                                        └─ 감사 로그(Postgres)
문서 갱신 → kb-worker(30분 주기) → 파싱/청킹 → 임베딩 → pgvector
```

## B-5. 장애 대응 런북

| 증상 | 확인 | 조치 |
|---|---|---|
| 답변이 “근거 없음”만 반환 | `kubectl logs deploy/kb-worker -n kb --tail=100` 에서 인덱싱 오류 확인 | 워커 재시작 `kubectl rollout restart deploy/kb-worker -n kb` → 재인덱싱 `kubectl exec -it deploy/kb-api -n kb -- python -m app.reindex --since 7d` |
| 응답이 8초 이상 | `kubectl top pod -n kb` 로 ollama 메모리 확인 | `OLLAMA_MAX_LOADED_MODELS=1` 확인, 모델 q4 강제, 필요 시 파드 재시작 |
| 파드 `CrashLoopBackOff` | `kubectl describe pod -n kb <pod>` Events 확인 | Secret 누락/DB 접속 확인 → `kubectl get secret -n kb` |
| `ImagePullBackOff` | 이미지 태그·레지스트리 주소 | 폐쇄망이면 `docker load` 후 태그 일치 확인 |
| 표 숫자가 깨져 인용 | 해당 PDF 파서 로그 확인 | OCR 재처리 `python -m app.ingest --file <pdf> --ocr` |
| 개인정보가 답변에 노출 | 감사 로그에서 질의 추적 | 즉시 해당 문서 인덱스 제외, 마스킹 규칙 보강, 사고 리포트 |
| 전체 다운 | `kubectl get nodes`, Ingress 상태 | 노드 재부팅 → `systemctl status k3s` → 백업에서 DB 복구 |

**원칙**: 30분 안에 원인을 못 찾으면 **롤백**(이전 이미지 태그) 후 원인 분석. 서비스 복구가 원인 규명보다 먼저입니다.

## B-6. 백업·복구

```bash
# 백업 (매일 03:00 cron)
kubectl exec -n kb deploy/pgvector -- pg_dump -U kb_app kb | gzip > /backup/kb-$(date +%F).sql.gz
# 복구 (리허설 포함)
gunzip -c /backup/kb-2026-11-27.sql.gz | kubectl exec -i -n kb deploy/pgvector -- psql -U kb_app kb
```
- 보관: 일 30일 / 월 12개월, 오프사이트 1부.
- 임베딩은 재생성 가능하므로 문서 원본과 DB만 백업(모델 파일은 해시로 무결성 검증).
